# Отключение IPv6 на Linux VPS — 2.3.3

Один автономный `ipv6.sh`: проверка совместимости → backup → применение → проверка сети → одна команда подтверждения. Запускать от root. Скрипт не устанавливает пакеты, не меняет загрузчик и не перезагружает сервер.

2.3.3 удаляет IPv6 DNS, адреса и маршруты из поддерживаемой конфигурации cloud-init v1, сохраняя IPv4 DNS, поисковые домены и DHCPv4. Кэш cloud-init используется для чтения. При конфликте сетевых владельцев или риске изменения IPv4 после регенерации скрипт останавливается до сетевых изменений.

До применения скрипт проверяет обе копии backup и убеждается, что systemd загрузил watchdog и включил его на следующую загрузку. После применения и восстановления проверяет работоспособность IPv4-интерфейса и повторяет запрос DNS, если он успешно выполнился до применения.

2.3.1 исправляет ложный concurrent config modification, когда Netplan пересоздаёт идентичный `/run/systemd/network/10-netplan-*.network` при `daemon-reload` watchdog. Для этих генерируемых файлов не сравнивается mtime; содержимое, права, uid/gid и ACL/xattrs остаются под контролем. Постоянные исходники проверяются по-прежнему. Backup 2.3 читается без изменения.

## Запуск и подтверждение

```bash
bash ipv6.sh
```

После `AWAITING_CONFIRMATION` откройте новое SSH-подключение по IPv4 и выполните в нём **одну готовую команду** из вывода. Новое подключение проверяет доступность снаружи. При подтверждении движок повторно проверяет локальное состояние сети. Для работы через консоль проверку внешнего SSH выполните отдельно перед подтверждением.

По умолчанию независимый watchdog даёт 600 секунд с момента его постановки; вывод показывает фактически оставшееся время после применения. Без подтверждения watchdog восстанавливает исходное состояние. При следующей загрузке неподтверждённая операция восстанавливается сразу после network.target, без нового десятиминутного интервала; календарные часы для срока не используются. Обнаруженная ошибка применения запускает восстановление сразу. Успешное подтверждение повторно проверяет сеть, фиксирует COMMITTED и отменяет страховку. NOOP не создаёт транзакцию и не требует подтверждения.

Отдельные операции:

```bash
bash ipv6.sh --check
bash ipv6.sh --status
bash ipv6.sh --confirm /var/lib/mist-ipv6/tx-ИМЯ
bash ipv6.sh --restore /var/lib/mist-ipv6/tx-ИМЯ
```

`--confirm` только фиксирует результат; `--restore` только восстанавливает. Откаченную, истёкшую или незавершённую до reboot транзакцию подтвердить нельзя. Для восстановления сохранённой операции предпочтителен её собственный `tool.sh`; backup 2.1/2.2 читается также текущим движком. Не восстанавливайте старую операцию поверх более нового состояния.

## Короткая команда Xshell

`python tools/command.py --ref <полный SHA коммита>` создаёт короткую строку «Отправить Строку»: URL, закреплённый на коммите → файл `/root/mist-ipv6-<начало SHA-256>.sh` с `umask 077` → проверка SHA-256 **полного файла** → запуск только при совпадении. Проверенный файл сохраняется. В команде нет `$`, переменных и подстановок; добавлять обратные слеши не нужно. Для Xshell добавляется только буквальное завершающее `\r`. `--output Xshell.txt` сохраняет точное поле без лишнего перевода строки.

Добавьте `--check` к генератору, чтобы команда после проверки SHA-256 только проверила совместимость. Для вставки в обычный терминал используйте `--bash --output Bash.txt`. Для поля «Отправить Строку» генератор по умолчанию добавляет буквальное `\r`.

Целевой тест генератора: `python3 -B -m unittest discover -s tests -p test_command.py -v`. Он проверяет точные файлы команд, синтаксис Bash и цепочку curl → sha256sum → Bash с безопасным тестовым скриптом через локальный HTTP. Эти проверки не запускают сетевой движок и не считаются проверкой интерфейса Xshell.

## Необязательный запуск с ПК

```powershell
python -X utf8 ipv6_ssh.py server-217
```

Малая обёртка использует существующий OpenSSH и его конфигурацию, передаёт соседний `ipv6.sh`, сохраняет и проверяет его на сервере. Показывает результат и ту же команду подтверждения. Самостоятельно не подтверждает и не восстанавливает после успешного apply. `--confirm TX`, `--restore TX`, `--check`, `--status` лишь передают соответствующую операцию движку. Собственных правил определения сети/транспорта и запрета multiplexing нет. Дождётся синхронного восстановления сервера; потерю транспорта обнаруживает штатный OpenSSH keepalive.

## Что сохраняется

Работа только в host namespace полной VM/хоста. Обнаруженные контейнеры (включая LXC/OpenVZ VPS) отклоняются до записи штатным systemd-detect-virt; их native-поддержка не заявляется. До сетевой записи — проверенный backup с зеркалом и один независимый systemd watchdog. Flock защищает от параллельного запуска; обнаруженное чужое изменение запрещает перезапись при apply/restore/confirm. Исходники и состояние сохраняются в `/var/lib/mist-ipv6/tx-*`.

Определяется действительный владелец настроек: Netplan с объединением файлов, прямой networkd, NetworkManager, ifupdown/ifupdown2. IPv6 убирается из постоянного источника, затем проверяется на каждом интерфейсе. IPv4, маршруты, policy rules, DNS/resolv.conf и MTU проверяются по снимку. Время аренды DHCP нормализуется; потеря адреса или маршрута остаётся ошибкой. Cloud-init не отключается целиком.

Мосты, VLAN, bond, Docker и VPN сами по себе не причина STOP. Контейнерные namespaces и конфиги SSH/UFW/Reality/Caddy/RemnaNode не меняются. Отсутствие IPv4-адреса и default route на действующем интерфейсе, реальная IPv6-зависимость, конфликт владельцев или неподдерживаемая схема отклоняются до записи с конкретной причиной. Узкая проверка парных сокетов chronyd с IPv4-источниками сохранена.

## Границы проверки

Нужны root, Bash, Python >=3.8, systemd, iproute2 и getent. Netplan/cloud-init требует уже установленный PyYAML; NetworkManager — nmcli и busctl.

Для 2.3.1 выполнены 12 целевых и соседних unit-тестов и native-воспроизведение Netplan generator при настоящем `systemctl daemon-reload`: V2.3 ложно отказывает, 2.3.1 принимает идентичный файл с новым mtime и отклоняет настоящее изменение содержимого. Права, uid/gid и xattrs дополнительно проверены на реальной файловой системе в unit-тестах. Полная матрица 2.3 не повторялась.

Дополнительно 2.3.1 проверена на VPS с Ubuntu 24.04.5, ifupdown, статическим IPv4 на ens3 и systemd-resolved: применение с backup/watchdog, COMMITTED после внешнего входа, повторный NOOP, реальная перезагрузка и NOOP после неё. IPv4, шлюз, DNS и MTU сохранены; networking.service после удаления постоянной IPv6-конфигурации запускается успешно.

Текущий native-контур: Ubuntu 24.04.5, Linux 6.8, Netplan/networkd, resolved, chronyd 4.5 и tmux 3.4. В отчёте комплекта отдельно указаны прогоны текущего SHA, повторно используемые результаты неизменённого сетевого кода и unit-тесты с подменами. Последние не доказывают работу настоящего менеджера. Native-прогоны старой V2 не приписываются текущему файлу. Cloud-init + ifupdown2 boot остаётся PARTIAL; native ifcfg-rh и enforcing SELinux не подтверждены. Поддержка любого Linux VPS не заявляется.

## Исходники и сборка

`src/engine.py`, `src/display.py`, `tools/engine-prefix.txt` → `python tools/build.py` → один автономный `ipv6.sh`. `python tools/build.py --check` проверяет воспроизводимость без записи. Linux-регрессии: `python3 -B -m unittest discover -s tests -v`; при повторном staging исключайте чужой старый pyc-cache.

Из версии 2.2 удалены ancestry sshd, TCP inode/возраст/endpoint proof, привязка клиента tmux, popup/nonce и обязательное новое подключение. Сетевые адаптеры и восстановление не переписывались. Контрольные суммы всех выдаваемых файлов — в `SHA256SUMS`. Raw evidence и серверные backups остаются в локальном комплекте, без credentials в GitHub.

Main обновляется только после отдельного GO владельца. Перезагрузка рабочей VPS требует отдельного GO.
